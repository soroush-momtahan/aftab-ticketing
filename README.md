# ساختار کلی

برای این پروژه از معماری `clean Architecture` استفاده شده است. هر چند که اگر در یک پروژه modular monolith یا microservice بودیم می شد با توجه به اینکه Ticketing منطق پیچیده ای ندارد از معماری `Vertical Slice` استفاده کرد.

برای بحث نمایش از یک Read Db جدا استفاده شده است تا کارمان برای بحث نمایش راحت تر باشد و به نوعی fetch کردن داده ها از دیتابیس بصورت خطی انجام بشه تا به نوعی نیاز نباشه دو جدول ticket و replyTicket رو بهم هم join کنیم و همچنین نیاز بود نام نویسنده هر تیکت رو هم داشته باشیم و اگر از Read Db استفاده نمی شد نیاز بود بعد از دریافت تیکت ها دونه دونه درخواست میفرستادیم تا نام نویسنده هر تیکت رو هم بگیریم و این سرعت در فرانت اند رو به شدت پایین می آورد.

برای بحث ذخیره تیکت در read db از outbox pattern استفاده شده تا پیام ها قابل اتکا باشند به این صورت که ابتدا پیام ها در یک جدول به اسم OutBoxMessage ذخیره می شوند و در گام بعد یک worker داریم که با استفاده از کتابخانه Quartz نوشته شده و کارش خواندن پیام ها از دیتابیس و دادن آن پیام ها به DomainEventHandler مربوطه هست. در نهایت نیز در یک جدول دیگر تحت عنوان OutboxMessageConsumer مشخص میشه که هر event توسط چه Handler ای مدیریت شده است.

برای بحث ذخیره داده ها در دیتابیس از repository pattern و اینترفیس UnitOfWork استفاده شده است. استفاده از UnitOfWork باعث شده تا بطورکلی ذخیره رکورد در جدول ها بصورت تراکنشی انجام شود و همچنین باعث شده تا به کمک آن بتوانیم event های دامنه رو نیز بصورت تراکنشی در دیتابیس ذخیره کنیم و این تضمین وجود داشته باشد که مثلا اگر تیکت به هر دلیلی در دیتابیس درج نشد پیامی هم در جدول OutboxMessage درج نشود تا سیستم در وضعیت ناپایدار قرار نگیرد که این مورد به کمک interceptor انجام می شود.

منطق Ticket در لایه Domain قرار دارد ، سعی شده لایه Domain منطبق با رویکرد DDD باشد ؛ مثلا از ValueObject استفاده شده البته نه برای همه property ها و در واقع Aggregate هایی داریم.
هم کاربر و هم ادمین می تواند برای یک تیکت پاسخ ثبت کنند(البته کاربر فقط می تواند برای تیکت خودش پاسخ ثبت کند که این موضوع در لایه presentation توسط یک Policy مدیریت شده) ، با این تفاوت که اگر ادمین پاسخی برای یک تیکت ثبت کند وضعیت تیکت به حالت InProgress در می آید اما اگر کاربر بعد از ثبت تیکت پاسخی به تیکت خودش بدهد وضعیت مسلما عوض نمی شود.

در لایه Application از CQRS Pattern استفاده شده ، در این لایه فقط سیم کشی هر دستور یا درخواست رو انجام می دهیم به نوعی در این لایه Feature هایی داریم که هر کدام Hander و DataModel خاص خودشون رو دارند. هر Handler تنها وظیفه صدا زدن interface ها یا متد های لایه Domain رو به عهده داره تا وظیفه ای که در قبالش هست رو به کمک این موارد رهبری کنه.

در لایه Presentation از minimal Api استفاده شده ، هر minimal Api تنها با یک CommandHandler یا QueryHandler در ارتباط هست و هیچ منطقی رو به تنهایی برعهده نمیگیره (البته در این مثال یکی از minimal api ها به اسم GetTicketsEndpoint یکم کار های بیزنسی میکنه که در آپدیت بعدی این مورد به لایه Application منتقل میشه) و به نوعی فقط یک پل ارتباطی هست. برای بحث مجوز های دسترسی از Policy ها استفاده شده است.

در لایه Infrastructure هم زیر ساخت و پیاده سازی های لازم برای پروژه انجام شده ، برای بحث security از AspIdentity استفاده شده ، اما سعی شده این مورد تنها برای بحث امنیت باقی بمونه و با AspIdentity مانند یک سرویس رفتار شده تا وابستگی ای در بقیه لایه ها به AspIdentity ایجاد نشه.

در لایه Api سیم کشی های کلی پروژه انجام شده.

در لایه OutboxWorker سم کشی لازم برای بحث Worker برای انجام فعالیتی در بازه های زمانی مشخص انجام شده.

در نهایت در لایه Host که مانند ثبت احوال سرویس هاست ، به کمک aspire تمامی سرویس ها رجیستر شده اند.

در لایه shared هم سعی شده موارد زیر ساختی مشترک قرار بگیره ، که الابته این پوشه Shared طی مراحل مختلف و طولانی به صورت تیکه تیکه از منابع مختلف جمع آوری شده و هنوز هم جای کار دارد.
